**27차 배포 후보:** 기록실의 SQL 집계 범위를 줄이고 중복 집계를 합쳤습니다. 기록 조회는 백그라운드에서 실행하며, 통산 조회의 첫 20명을 먼저 보여준 뒤 전체 명단을 갱신합니다. 검색·정렬은 캐시를 재사용하고 세이브 변경 시 결과를 폐기합니다. 사진은 표시 중인 행만 로딩합니다. [27차 측정·배포 검증 보고](reports/release27/RELEASE27_SUMMARY.md)를 확인하세요.

Windows 실행 파일은 `dist/IDOL_Manager/IDOL_Manager.exe`이며 `_internal`을 포함한 폴더 전체를 유지해야 합니다. 개인 사진·음악·세이브는 배포물에 넣지 않습니다. 빌드는 `requirements-build.txt` 설치 후 `.venv\Scripts\python.exe -m PyInstaller --noconfirm IDOL_Manager.spec`, `.venv\Scripts\python.exe tools\release27_manifest.py` 순서로 재현합니다. PowerShell 스크립트 실행이 허용된 환경에서는 `tools\build_release27.ps1`도 사용할 수 있습니다. 신규 PC/VM·실제 OS DPI·코드 서명·백신 환경 검증 여부는 보고서에서 구분합니다.

기존 프로젝트의 세이브를 계속 사용하려면 배포 폴더 내용(EXE와 `_internal` 등)을 기존 프로젝트 루트에 복사하고 그곳의 EXE를 실행하세요. 기존 `data/`, `assets/`를 옮기거나 덮어쓸 필요가 없습니다. `dist`의 EXE는 상위 프로젝트 폴더까지 세이브를 자동 탐색하지 않습니다. 기본 AppData에 게임이 이미 있다면 그 저장 파일을 우선 사용합니다. 이번 검증에서는 실제 AppData에 세이브를 만들지 않았습니다.

**26차 후속 안정화:** 기본 세이브 위치는 이제 `%LOCALAPPDATA%\IDOL_Manager\saves\idol_manager.sqlite3`입니다. 사용자 설정은 `config/`, 로그는 `logs/`, 썸네일은 `cache/`에 저장합니다. 프로그램 코드·번들 사진·기본 설정 템플릿은 설치 폴더에서 읽기만 합니다. 기존 `data/` 또는 `saves/`의 단일 세이브는 첫 실행 시 SQLite 백업 API로 검증·복사하며, 원본을 삭제하거나 이동하지 않습니다. 새 위치에 이미 세이브가 있으면 그 게임을 사용하고 이전 파일은 보존합니다. 이전 파일이 두 개면 임의 선택하지 않고 가져오기 안내와 함께 시작을 중단합니다. 가져오기 API는 `idol_manager.storage.import_save(source, user_paths())`이며 기존 목적지 덮어쓰기를 거부합니다.

사용자 추가 사진은 `%LOCALAPPDATA%\IDOL_Manager\user_assets\idols\`, 음악은 `user_assets\audio\bgm\default\`와 `battle\`에 넣을 수 있습니다. 기존 `assets/` 사진·음악도 계속 읽습니다. 직접 가져온 사진 경로는 절대 경로로 저장되므로 사용자 폴더를 수동 이동할 때에는 원본 경로를 유지해 주세요. `IDOL_MANAGER_USER_DATA` 환경 변수로 데이터 루트를 지정할 수 있습니다(테스트/별도 프로필용). 이 변수의 경로를 실제 세이브와 테스트가 공유하지 않도록 하세요.

작은 선수단 창은 오른쪽 스크롤로 편성·리더·표 페이지 버튼에 접근합니다. 26차 기존 보고서는 그대로 유지하며 새 결과는 [후속 QA 보고서](reports/release_qa/QA_FOLLOWUP_SUMMARY.md)에 기록합니다. PyInstaller 리소스 경로 분기는 지원하지만 실제 EXE 제작·신규 PC 설치 검증은 별개입니다. 아래 `data/` 설명과 단계별 테스트 수치는 이전 개발 당시 기록입니다.

**분할 방출 채무로 드래프트가 막힌 경우:** 기획사 재정 화면에서 플레이어 기획사를 선택하고 남은 위약금을 확인한 뒤 **방출 위약금 전액 상환**을 사용할 수 있습니다. 충분한 현금이 있을 때만 확인 창을 거쳐 남은 예정·연체 위약금을 한 번 지급합니다. 최초 위약금·기존 납부 회차는 보존하고 이후 자동 청구는 중단합니다. 자동으로 대신 상환하거나 부족한 자금을 지급하지 않습니다.

AI도 같은 공개 범위만 평가합니다. 기존 세이브는 백업 후 DB 버전 **9**로 추가 확장하며 지명·경기 결과를 재계산하지 않습니다. [13차 사용법·변경 파일·보존 검증·전체 테스트 결과](docs/13차_드래프트_추정치.md)를 확인하세요.

**12차 특별전:** 사이드바 **특별전**에서 정규 4·8·12·16·20·24주차 일요일의 상위·하위 5자 대결과 후속 4자 대결을 진행합니다. 그룹 편성 확정 → 출전자 선택 → 대결 시작 → 관전 또는 스킵 → 남은 단계 순서로 진행하세요. 후속 출전자는 최초 10명 중 부상자를 제외하고 1군 우선으로 선택합니다. 세 단계가 완료되면 다음 월요일로 진행할 수 있습니다. 기존 세이브는 백업 후 DB 버전 8로 추가 확장하며, 정규 결과·원본 능력치·특별전 종류를 재생성하지 않습니다. [12차 사용법·정책·전체 변경 파일·검증 보고](docs/12차_특별전.md)를 확인하세요.

**BGM:** `assets/audio/bgm/default/`와 `assets/audio/bgm/battle/`에 MP3·WAV를 넣으면 자동 셔플 재생합니다. 상단 **♪ BGM**에서 켜기·음소거·일시정지·볼륨·다음 곡·목록 새로고침을 조작합니다. 실제 경기 관전 탭에서만 배틀 음악을 사용하며 일반 화면끼리는 곡을 유지합니다. 볼륨·음소거·켜기 상태는 SQLite와 별개인 `data/bgm_settings.json`에 저장합니다. [BGM 구조·사용법·테스트 및 Windows 재생 보고](docs/BGM_시스템.md)를 확인하세요.

현재 버전에는 **정규 경기 UI**가 추가되었습니다. 사이드바 **정규 경기**에서 오늘 경기와 플레이어 출전자를 선택하고, 약 30초 관전·동일 결과 스킵·개인 기록·리그 순위를 확인합니다. **AI 경기 빠른 진행**으로 다른 기획사 경기를 처리한 뒤 당일 경기를 모두 마치면 다음 날짜로 진행합니다. 과거 결과는 **저장된 경기 결과**에서 조회합니다. 두 설정 파일을 확인하고 기존 테스트가 통과한 뒤 구현했으며 설정·28주 시즌·기존 세이브를 변경하지 않았습니다. [사용법·변경 파일·검증 보고](docs/정규_경기_UI.md)를 확인하세요.

정규 경기 UI 최종 검증은 Windows Qt 플랫폼에서 **178개 테스트 전체 통과(100.708초)**입니다. 실제 30초 관전과 스킵의 결과 일치, 실제 세이브 복사본의 최초 편성부터 첫 수요일 경기·목요일 진행까지 확인했습니다. 원본 27개 테이블·이미지 320개·두 설정 파일은 변경 전 해시와 일치합니다.

날짜·리더 집중 수정에서는 현재 날짜를 모든 화면 위의 공통 상단에 표시하고, 리더 버튼의 미편성·요일 제한 사유를 명시했습니다. UI와 서비스는 동일한 게임 날짜의 월요일 판정을 사용하며, 기존 편성과 리더는 재실행 시 그대로 불러옵니다. 실제 세이브의 날짜와 선수단은 변경하지 않았습니다. [원인·수정·GUI 검증 보고](docs/날짜_리더_수정_검증.md)를 확인하세요.

후속 교착 수정에서는 **드래프트·최초 편성·플레이어 양군 리더 지정 전 날짜 진행을 서비스에서도 차단**합니다. 이미 수요일로 진행한 초기 세이브는 안전 조건을 만족하면 상단의 **초기 날짜 복구** 버튼으로 복구할 수 있습니다. **기본은 취소이며, 명시적으로 승인해야 SQLite 백업 후 날짜와 날짜 수정 버전만 바꿉니다.** 실제 세이브는 자동으로 수정하지 않습니다. [복구 조건·사용 순서·검증 보고](docs/초기_편성_교착_복구.md)를 확인하세요.

교착 수정 최종 검증은 Windows Qt 플랫폼에서 **162개 테스트 전체 통과(66.810초)**입니다. 실제 원본은 수요일 상태를 유지했으며 기존 27개 테이블과 이미지 320개의 해시가 작업 전과 일치합니다. 복구 시험은 복사본에서만 실행했습니다.

## 실행

1. **64비트 Python 3.12 이상**을 설치합니다. 이 프로젝트는 Python 3.13.3에서 개발 및 테스트했습니다.
2. `실행하기.bat`를 더블클릭합니다. 최초 실행 시 프로젝트 내부 `.venv`를 만들고 `requirements.txt`의 PySide6를 설치하므로 인터넷 연결이 필요합니다. Python 런처, PATH, 사용자별 Python 설치 폴더에서 실행 환경을 찾습니다.
3. 기존 게임이 있으면 저장 내용을 그대로 불러오고 필요한 스키마 마이그레이션을 자동 적용합니다. **기존 게임을 유지하려면 새 게임을 생성할 필요가 없습니다.**
4. 처음 시작하는 경우 창 왼쪽의 **새 게임 생성**을 클릭합니다. 기존 게임이 있으면 교체 확인창이 나옵니다. 동의하여 새 게임을 다시 만들면 인물 수치·후보·소속 상태와 기획사 자금이 새 게임 기준으로 교체됩니다.

직접 실행하려면 Python 3.12 이상으로 다음 명령을 실행합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

기본 `python`이 3.10이라면 `py -3.13` 또는 설치된 Python 3.12 이상의 `python.exe` 전체 경로로 가상 환경을 생성하세요. 이 PC에서는 `C:\Users\정승찬\AppData\Local\Programs\Python\Python313\python.exe`를 사용할 수 있습니다. 배치 실행기는 이 설치 폴더도 탐색합니다.

## 게임 날짜와 경기 일정 사용법

기존 세이브를 실행하면 백업 후 최신 DB 버전 **11**로 확장합니다. 성장 규칙은 도입 이후의 정상 날짜 진행부터 적용하며 과거 주간 정산을 소급 지급하지 않습니다. 기존 시즌·구간·주차·요일과 585경기 일정·특별전·지명·선수·경기 결과를 보존합니다. 기존 비시즌 저장에는 과거 포스트시즌을 소급 생성하지 않으며 다음 시즌부터 적용합니다. 새 게임 날짜는 **시즌 1 · 정규 1주차 · 월요일**부터 시작하고, 정규 24주 + 포스트시즌 3주 + 비시즌 4주 = **217일**입니다. 정규 마지막 일요일 다음은 포스트시즌 첫 월요일, 포스트시즌 마지막 일요일 다음은 비시즌 첫 월요일, 비시즌 4주 일요일 다음은 다음 시즌 첫 월요일입니다.

- 모든 화면의 상단에 현재 게임 날짜와 **하루 진행** 버튼이 있습니다. 드래프트 → 최초 선수단 편성 → 양군 리더 지정을 마쳐야 날짜를 진행할 수 있습니다. 교체·리더 변경은 게임 날짜가 월요일일 때만 허용합니다.
- **경기 일정**에서 이번 주, 전체 24주, 특정 주차, 기획사별 일정을 조회합니다. 주간 공개 규칙에 따라 미래 주차의 정규 상대·콘텐츠 및 특별전 종류는 `월요일 공개 예정`으로 표시하며, 해당 주 월요일부터 공개합니다.
- 실제 경기 시각은 만들지 않습니다. 같은 날짜에 **1차 경기 / 2차 경기**만 사용합니다. 경기 번호는 시즌 내 고유 표시 순서이며 실제 시각이 아닙니다.
- 콘텐츠·주요 능력치·출전 인원 범위는 기획서 6장 그대로입니다. 범위형 인원은 경기 당일 한 번 추첨해 DB에 저장하며 양측 기획사가 동일한 값을 사용합니다. 재실행하거나 같은 날짜를 다시 불러와도 재추첨하지 않습니다.
- **정식 하루 진행은 미처리 경기·특별전이 있는 날짜를 넘어가지 않습니다.** 이미 지나간 날짜에 미처리 경기가 있더라도 중단합니다. 정규 경기 메뉴에서 당일 경기를, 특별전 메뉴에서 상위·하위 그룹과 후속 대결을 완료한 뒤 진행하세요. 자동 완료하거나 건너뛰지 않습니다.
- **테스트용 날짜 미리보기**는 순수 날짜 계산만 합니다. 217일 뒤의 다음 시즌 등을 확인할 수 있지만 실제 게임 날짜, 경기 상태, 세이브에는 쓰지 않습니다. 테스트용 `진행 허용` 우회 플래그를 정식 API에 두지 않습니다.
- 시즌 번호가 바뀌어도 이번 단계에서는 인물 나이·능력치·잠재력·기획사 자금·선수단·드래프트 기록을 바꾸지 않습니다. 이후 시즌의 일정만 새로 생성합니다.

### 확정 일정 규칙과 출처

기준 파일은 `docs/IDOL_Manager_기획서_2026-10-26.txt`의 5장·6장·8장과 사용자의 후속 확정 답변입니다. `config/season_schedule.json`에 규칙 버전·출처·30종 콘텐츠와 출전 인원·주요 능력치를 분리했습니다.

- 정규 경기 **585건**, 기획사당 **117경기**, 기획사 쌍 45개가 **각 13회** 대결합니다. 13회의 완전 라운드로빈을 무작위로 섞어 배치합니다.
- 수~일 120일 중 특별전 일요일 6일을 제외한 **114일**이 일반 경기일입니다. 이 중 **3일을 무작위 더블헤더**로 뽑습니다. 일반 111일에는 5경기씩, 더블헤더 3일에는 10경기씩 진행하며 각 경기 순서에 10개 기획사가 한 번씩 참가합니다. 더블헤더가 같은 주에 몰리는 것도 허용합니다.
- 콘텐츠 30종 중 무작위 15종을 20회, 나머지 15종을 19회 배정합니다. **연말시상식은 21~24주차에만** 배정합니다. 선수 능력치나 잠재력을 일정 생성에 사용하지 않습니다.
- 특별전은 **4·8·12·16·20·24주 일요일**에 6회입니다. 대학축제 / K-POP 페스티벌 / 아이돌 체육대회를 매번 각 1/3로 독립 추첨합니다. 같은 종류의 반복도 허용하며 정규 585경기에 포함하지 않습니다. 이번에는 날짜·종류·예정 상태만 저장하고 순위별 그룹, 후속 대결, 판정과 승점은 구현하지 않습니다.
- 한 시즌의 상대·날짜·경기 순서·콘텐츠·특별전 종류는 저장 후 덮어쓰지 않습니다. 설정 파일이 바뀌어도 기존 시즌은 당시 규칙 스냅샷과 대진을 유지하고 다음 시즌부터 새 설정을 사용합니다.

**미확정 세부 규칙은 임의로 추가하지 않았습니다.** 실제 시각(`actual_match_times`), 기획사별 콘텐츠 출현 하한·상한(`per_agency_content_minimum` / `per_agency_content_maximum`), 동일 상대 연속 경기 제한(`same_opponent_consecutive_day_limit`)은 설정에서 `null`로 둡니다. 현재는 확정된 리그 전체 콘텐츠 균등 조건만 강제하며, 기획사별 추가 편중 한도나 연속 대진 제한을 지어내지 않습니다. 비어 있지 않은 미확정 설정을 넣으면 적용을 중단하고 안내합니다.

### 날짜 변환과 저장 보호

기존 `game_clock.management_date`의 실제 날짜는 백업과 `legacy_game_clock` 감사용 테이블에 보존합니다. 기존 단계에는 누적 게임 일수가 없으므로 **기존 요일을 시즌 1 정규 1주차의 같은 요일로** 옮깁니다. 기존 `2026-10-26` 월요일은 0일차, 즉 게임 시작일로 바뀝니다. 화요일 세이브는 1일차로 옮겨 월요일 제한을 갑자기 풀지 않습니다. 잘못된 기존 날짜는 임의 보정하지 않고 전체 마이그레이션을 취소합니다. 게임 화면과 선수단 판정은 실제 연월일을 사용하지 않으며, 백업 파일명과 기존 감사 시각만 실제 시간을 유지합니다.

현재 날짜는 `game_clock.absolute_day`와 수정 버전으로 저장합니다. 날짜 진행·경기 당일 인원 추첨·다음 시즌 일정 생성은 하나의 SQLite 트랜잭션입니다. 동시에 같은 날짜를 진행하려는 요청 중 하나만 적용되며, 실패하면 날짜와 일정 모두 되돌립니다. 같은 시즌 중복 생성은 시즌 기본 키, 같은 경기 순서의 기획사 중복 참가는 DB 고유 제약과 외래 키로 차단합니다. 일정이 누락되거나 설정이 미확정이면 조용히 빈 시즌으로 진행하지 않습니다.

## 선수단 관리 사용법

1. **기존 세이브를 그대로 실행**하고 왼쪽 **선수단 관리**를 누릅니다. 드래프트 미완료 상태에서는 안내만 표시하며 선수 능력치를 읽거나 최초 편성을 확정하지 않습니다.

## 화면에서 최초 드래프트 진행하기

1. 기존 세이브를 유지하려면 새 게임을 만들지 말고 **최초 드래프트** 메뉴를 엽니다.

5. 나머지 기획사는 후보 중 무작위로 자동 지명합니다. **다음 내 차례까지 빠르게**로 속도를 높일 수 있고 내 차례에는 자동으로 멈춥니다. **AI 일시정지 / AI 계속**도 사용할 수 있습니다. 명단 메뉴로 이동하거나 창을 닫으면 자동 진행은 멈춥니다. 다시 드래프트 화면에 들어오면 저장된 다음 차례부터 이어집니다.
6. 매 지명은 즉시 저장됩니다. 160번이 끝나면 기획사별 16명, 미지명 후보 40명을 검증하고 완료 상태로 잠급니다. 드래프트 직후에는 프로 편성 대기 상태이며 **선수단 관리**에서 1·2군을 별도로 편성합니다. 미지명 40명을 FA로 자동 전환하지 않습니다.

화면에는 현재 라운드·전체 지명 번호·현재 기획사·남은 후보·해당 라운드의 10개 기획사 순서·기획사별 지명 인원·전체 지명 이력을 표시합니다. 큰 창에서는 10개 기획사 순서를 함께 볼 수 있고 작은 창에서는 표를 스크롤할 수 있습니다. 후보 이름 검색과 열 정렬을 지원합니다. 후보 표는 사진·이름·나이 3열이며 능력치·건강·평균·성장 유형·잠재력·시장가치를 UI 데이터나 툴팁에 전달하지 않습니다.

이미 엔진만으로 시작해 플레이어 기획사가 저장되어 있지 않은 특수한 세이브는 기획사를 임의로 지정하지 않고 안내합니다. 이번 UI로 시작한 드래프트는 선택한 기획사와 순서를 저장하므로 그대로 재개할 수 있습니다.

## 사용법과 공개 범위

- `assets/idols/` 및 그 하위 폴더의 JPG, JPEG, PNG, WEBP를 확장자 대소문자와 관계없이 읽습니다. 파일명에서 확장자를 뺀 이름을 사용합니다. 한글·공백을 지원합니다.
- 사진 경로만 DB에 저장합니다. 원본 사진은 이름 변경, 수정, 이동, 삭제하지 않습니다. 캐시는 `data/thumbnails/`에 별도로 생성합니다.
- 같은 이름은 동일 인물로 간주합니다. 유니코드 NFC 정규화, 앞뒤 공백 제거, 영문 대소문자 구분 없는 이름 키로 중복을 방지합니다. 정렬한 상대 경로 중 첫 파일을 선택하며, 동일 이름의 여러 사진은 한 인물로 등록됩니다. 동명이인을 별개 인물로 구분하는 기능은 이번 범위에 포함하지 않습니다.
- ID는 정규화한 이름으로 만든 고정 UUID입니다. 재등록·재실행에도 유지됩니다. 새 게임은 현재 폴더에서 인식되는 인물 전체를 대상으로 생성됩니다.
- 새 게임마다 최초 후보는 무작위 200명입니다. 전체가 200명보다 적으면 전원을 후보로 지정합니다. 나머지는 DB에 미등장 상태로 저장하며 명단에 노출하지 않습니다.
- 일반 명단은 **사진·이름·가상 나이·상태**만 표시합니다. 능력치, 평균, 건강, 유형, 잠재력은 표·툴팁·사용자 데이터 역할에 전달하지 않습니다. 미등장 인물의 이름·사진·나이도 표시하지 않습니다.
- 검색창은 이름의 일부로 검색합니다. 열 머리글을 누르면 오름차순/내림차순 정렬합니다. 나이는 숫자로 정렬합니다. 열 너비를 조절할 수 있고 가로·세로 스크롤을 지원합니다.
- 사진이 삭제되거나 손상되면 대체 이미지로 표시하며 저장된 인물은 유지됩니다. 사진 폴더가 비어 있어도 프로그램이 실행됩니다. 사진 없이 새 게임을 생성하면 안내합니다.
- 재실행 시 추가 사진은 인물 카탈로그에 등록되지만 진행 중인 게임의 후보나 수치는 바뀌지 않습니다. 추가 인물은 다음 새 게임에 포함됩니다. 사진 경로 변경은 같은 이름이면 갱신됩니다.
- 명단 위 선택 상자에서 **최초 드래프트 후보** 또는 기획사를 선택합니다. 기획사별 프로 편성 대기·1군·2군·연습생 명단과 현재 자금을 조회할 수 있습니다. 검색·정렬은 선택한 명단에 적용됩니다. 최초 드래프트 전에는 기획사 명단이 비어 있는 것이 정상입니다.

## 최초 드래프트 내부 API

`GameService.draft`가 기존 `DraftEngine`을, `GameService.draft_session`이 플레이어 선택·UI 공개 스냅샷·AI 연결을 제공합니다. 다음은 Python 내부 API 예시이며 실제 게임은 위 화면 절차를 사용하세요. UI로 재개하려면 반드시 기획사를 먼저 저장합니다.

```python
from idol_manager.config import ROOT
from idol_manager.service import GameService

service = GameService(ROOT)
draft = service.draft
service.draft_session.select_agency("ador")
print(draft.age_issues())             # 규칙을 벗어난 후보의 공개 정보만 확인
state = draft.start()                 # 16세 후보 등이 있으면 DraftError로 차단
turn = state.next_turn
candidates = draft.available_candidates()
if turn is not None and candidates:
    result = draft.pick(
        turn.agency_id,
        candidates[0].id,
        expected_pick_number=turn.pick_number,
    )
```

기획사 10개·미배정 최초 후보 200명·후보 나이 17~26세·기존 소속 없음이 시작 조건입니다. 1라운드 순서를 한 번 무작위로 결정하고 짝수 라운드는 반대로, 홀수 라운드는 원래 순서로 16라운드 전체 160턴을 저장합니다. `start()`를 다시 호출해도 재추첨하지 않습니다. 재실행하면 `state()`, `turn_order()`, `picks()`로 같은 순서와 다음 지명을 불러옵니다.

플레이어와 AI는 **동일한 `pick(agency_id, person_id, expected_pick_number=...)` 인터페이스**를 사용합니다. 현재 차례의 기획사만 지명할 수 있고 전체 지명 번호를 명시해야 합니다. 같은 기획사가 10번·11번처럼 연속으로 지명하는 스네이크 경계에서도 오래된 요청을 재사용할 수 없습니다. 지명 명령은 `BEGIN IMMEDIATE`로 직렬화하고, 중복·순서 제약과 SQLite 트리거로 지명 결과·임시 프로 소속·완료 상태를 같은 트랜잭션에 저장합니다. 실패하면 해당 지명을 전부 취소합니다.

`available_candidates()`의 `BlindCandidate`는 고유 ID와 **사진 경로·이름·나이**만 가집니다. 드래프트 엔진은 지명에 현재 능력치·평균·건강·유형·잠재력을 조회하거나 평가하지 않습니다. 드래프트 AI는 별도 `ai_policy.py`의 `RandomBlindPolicy`로 무작위 ID를 선택하며 SQLite 연결을 받지 않습니다. 드래프트 이후의 선수단 AI는 별도 `squad_policy.py`에서 공개된 현재 능력치만 평가합니다. 지명 직후 상태는 `pro_pending`(프로 편성 대기)이며 최초 선수단 편성 후 `first_team` / `second_team`으로 바뀝니다.

160번 지명 직후 각 기획사의 소속이 정확히 16명이고 미지명 후보가 40명인지 확인합니다. `undrafted_candidates()` 또는 DB 뷰 `initial_draft_undrafted`로 최종 40명을 식별할 수 있습니다. 이 명단은 완료 전에 확정하지 않으며 FA로 자동 전환하지 않습니다. 최초 후보에 포함되지 않았던 미등장 110명도 이 40명에 섞이지 않습니다.

### 기존 16세 후보: 승인 전 값 유지

현재 세이브에는 16세 후보가 12명 있습니다. **승인 전에는 16세를 유지하며 드래프트 시작을 차단합니다.** 마이그레이션이나 앱 시작에서 보정 함수를 자동 호출하지 않습니다.

변경 없이 후보 나이 문제를 확인하려면:

```powershell
.\.venv\Scripts\python.exe tools\correct_draft_ages.py
```

사용자가 해당 16세 후보들의 나이만 17세로 변경하는 데 명시적으로 동의한 경우에만 다음 명령을 실행합니다:

```powershell
.\.venv\Scripts\python.exe tools\correct_draft_ages.py --approve-age-16-to-17
```

이 명시적 승인 옵션이 없으면 나이는 바뀌지 않습니다. API로는 승인한 ID 목록을 지정하여 `draft.correct_legacy_ages(approved=True, person_ids=(...))`를 호출합니다. 나이가 현재 16세인 최초 후보만 대상으로 허용하고, 백업을 성공적으로 만든 후 나이 필드만 변경합니다. 승인 시각·변경 전후 나이·백업 경로는 `draft_age_corrections`에 기록합니다. 선택한 ID 일부만 보정할 수도 있으며 나머지 나이 문제가 남아 있으면 시작은 계속 차단됩니다. 다른 나이 이상값을 임의로 고치지 않습니다. 이미 시작된 드래프트에서는 이 보정을 허용하지 않습니다.

## 기획사·소속 구조와 마이그레이션

ADOR, BELIFT, BIGHIT, CUBE, DSPmedia, JYP entertainment, SM entertainment, SOURCE MUSIC, STARship, YG entertainment의 10개 기획사를 고정 ID로 등록합니다. 초기 자금은 각 **1,000,000,000원(10억 원)**이며 SQLite 정수로 저장합니다. 로고는 기존 파일의 상대 경로만 저장합니다.

기획사 준비 단계에서 DB `user_version`을 1에서 2로 올렸고, 이번 드래프트 엔진은 **버전 2 세이브를 보존하며 버전 3으로 마이그레이션**합니다. 기존 `people`, `game`, `idols`, `abilities`, `agencies`, 후보 연결과 소속 데이터는 그대로 유지합니다.

| 테이블 | 저장 내용 |
| --- | --- |
| `agencies` | 고정 기획사 ID, 이름, 로고 상대 경로, 현재 자금(원) |
| `roster_memberships` | 인물별 단일 소속 기획사와 경력 상태 |
| `initial_draft_candidates` | 기존 후보 인물 ID에 대한 외래 키 연결 |

| 경력 상태 | 의미 | 소속 기획사 |
| --- | --- | --- |
| `unassigned` | 미배정: 드래프트 후보·미등장 인물의 초기 상태 | 없음 |
| `first_team` | 프로 1군 | 필수 |
| `second_team` | 프로 2군 | 필수 |
| `trainee` | 연습생 | 필수 |
| `pro_pending` | 드래프트 지명된 프로, 1·2군 편성 대기 | 필수 |
| `fa` | FA | 없음 |
| `retired` | 은퇴 | 없음 |

경력 상태는 기존 `idols.status`의 후보/미등장 공개 상태와 별개입니다. 마이그레이션은 기존 인물을 모두 미배정으로 연결하고 임의 소속이나 FA 상태를 부여하지 않습니다. 기존 후보 200명은 재선발하지 않고 ID 그대로 연결합니다. 후보 조회는 후보 연결·기존 후보 상태·미배정 여부를 함께 확인하므로 소속 선수나 FA·은퇴 인물이 후보 목록에 섞이지 않습니다. 모든 조회에는 공개 정보만 전달하고 능력치·건강·평균·유형·잠재력을 노출하지 않습니다.

`GameService.agencies()`, `GameService.agency_roster(agency_id)`, `GameService.initial_draft_candidates()`로 UI와 별도로 조회할 수 있습니다. 기획사 조회는 프로 편성 대기 선수도 포함합니다. 드래프트 UI와 AI의 실제 지명 저장은 모두 기존 내부 API를 통합니다. 방출·은퇴 처리 동작은 추가하지 않습니다.

기존 DB 업그레이드 전 SQLite backup API로 `data/backups/*_before_v3_*_KST.sqlite3` 백업을 만들고 무결성을 확인합니다. 백업 실패 시 업그레이드를 시작하지 않습니다. 버전 3에서는 `draft_state`, `draft_turns`, `draft_picks`, `draft_age_corrections` 및 미지명 후보 뷰를 추가합니다. 소속 상태 CHECK 제약 확장을 위해 소속 테이블의 모든 행을 새 정의에 복사한 뒤 하나의 트랜잭션에서 교체합니다. 오류 발생 시 기존 버전과 데이터로 되돌립니다. 현재 버전인 DB를 다시 열면 재초기화하거나 자금을 다시 지급하지 않습니다. 지원 버전보다 높은 DB는 변경하지 않고 실행 오류를 안내합니다. 나이 보정은 별도 `*_before_age16_to17_*` 백업이 필요합니다.

4차 UI는 **`PRAGMA user_version=3`을 유지**합니다. 기존 버전 3 DB에 `player_settings`와 선택 잠금 트리거를 추가하는 호환 확장만 적용하며, 적용 전에 `*_before_v3_player_ui_*` 백업을 만듭니다. 확장은 하나의 트랜잭션이고 실패하면 모두 취소합니다. 이미 확장이 있으면 다시 적용하거나 선택을 초기화하지 않습니다. 선택 행이 없으면 미선택, 있으면 선택 완료이며 기획사 ID와 선택 시각이 저장됩니다. 드래프트 시작 후 다른 기획사로 변경하거나 선택 행을 삭제·교체하는 것은 DB에서도 차단합니다. 사용자가 확인하여 새 게임을 만들 때만 선택과 드래프트를 함께 초기화합니다.

5차 선수단 기능은 **버전 3→4**로 마이그레이션합니다. 기존 테이블의 행을 그대로 보존하고 `game_clock`(저장된 관리 기준일), `squad_formations`(편성 확정 및 수정 버전), `squad_leaders`(소속별 리더), `professional_history`(프로 경력)를 추가합니다. 변경 전 `*_before_v4_*` 백업을 만들고 스키마와 날짜·프로 경력 초기화를 한 트랜잭션으로 처리합니다. 버전 4를 재실행하면 기준일·편성·리더를 초기화하지 않습니다. 선수단 개편은 수정 버전을 확인하여 다른 창의 변경을 덮어쓰지 않으며, 정원과 프로→연습생 금지 및 리더 소속 일관성은 DB에서도 보호합니다. 실제 최초 편성은 사용자가 5명을 선택하고 확인하기 전까지 실행하지 않습니다.

| 공통 전체 능력 수준 | 목표 평균 40~70, 유형과 독립적으로 선택 |
| 특화형 | 50%, 특화 1~3개, 목표 평균보다 12~22 높게 배분 |
| 균형형 | 30%, 약한 특화 1~3개, 목표 평균보다 2~5 높게 배분 |
| 극단적 특화형 | 20%, 특화 1~3개, 목표 평균보다 28~40 높게 배분 |
| 잠재력 | 능력치 + 0~35, 최대 100 |

가중치는 각 인물에 독립적으로 적용되는 확률이므로 게임마다 실제 비율은 달라집니다. 능력치는 보컬, 댄스, 랩, 예능, 외모, 신체, 지성, 리더십의 8개이며 평균은 산술평균입니다. 잠재력은 능력치별로 별도 저장하고 현재 값 이상으로 제한합니다.

전체 능력 수준을 먼저 선택하고 유형에 맞게 총합을 배분합니다. 특화 능력치는 최대 100으로 제한하고, 나머지 능력치에 남은 총합을 배분한 뒤 합계를 바꾸지 않는 범위에서 편차를 줍니다. 따라서 동일한 평균 40~70의 어느 값에서도 세 유형이 모두 생성되며, 극단적 특화형이 유형 자체 때문에 낮은 평균으로 생성되지 않습니다. `spread`는 일반 능력치의 배분 편차를 조정합니다. 기본 범위에서는 특화 능력치 1~3개가 평균보다 높고 나머지는 평균 이하입니다. 전체 능력 수준을 0 또는 100 부근으로 설정하면 0~100 제한 때문에 유형 간 분포 차이가 줄어들 수 있습니다.

현재 새 게임의 최초 후보와 미등장 인물을 포함한 초기 인물 풀은 `initial_draft` 나이 규칙을 사용합니다. 생성 함수는 명시적인 나이 문맥을 받으므로 향후 연간 신인 규칙을 별도 키로 추가할 수 있습니다. 연간 신인 생성이나 등장 로직은 이번 수정에 포함하지 않습니다.

생성 규칙 변경은 **다음 새 게임부터** 적용됩니다. 기존 세이브의 나이·능력치·잠재력·후보 상태는 프로그램 재실행이나 버전 2 마이그레이션으로 다시 생성하지 않습니다. 기존 게임을 교체하려면 새 게임 생성 확인창에서 동의해야 합니다. 1차 생성 규칙 변경 전 DB 백업은 `data/backups/idol_manager_before_generation_20261027_010242_048293_KST.sqlite3`에 보관되어 있습니다.

1차 생성 규칙 검증 당시 12,000명 표본에서 특화형/균형형/극단적 특화형 비율은 각각 49.52%/30.16%/20.32%, 유형별 평균 능력치는 55.136/55.029/54.951이었습니다. 가상 나이는 모두 17~26세였습니다. 이번 2차 준비 작업에서는 해당 생성 함수를 변경하지 않았고 범위·확률·분포·잠재력 하한 테스트를 다시 실행합니다.

7차에서는 정규 경기 판정·결과와 개인 기록 저장 API를 추가했습니다. 기존 저장은 사전 백업 후 DB 버전 6으로 확장하며, 실행만으로 경기를 자동 진행하지 않습니다. 출전자별 60회 판정, 출전 리더 추가 2회, 동점 데스매치, 몰수패, 공개 현재 능력치만 사용하는 AI 출전, 중복·동시 요청 방지, 강제 종료 후 동일 입력으로 재개를 지원합니다. 미래 주차 특별전 종류는 해당 주 월요일부터 공개합니다. 파일 구성·테이블·API·세부 정책은 [7차 정규 경기 엔진 문서](docs/7차_정규경기_엔진.md)를 확인하세요.

7차 최종 검증은 Windows / Python 3.13.3 / PySide6 6.12.0에서 Qt `windows` 플랫폼으로 **136개 테스트 전체 통과(41.378초)**입니다. 기존 21개 테이블과 이미지 320개의 해시가 작업 전과 일치하며, 실제 세이브에는 경기 결과를 생성하지 않았습니다. 상세 보존 결과는 `.test-artifacts/match_verification.json`에 있습니다.

11차에서는 연속 출전일 피로, 건강·1군 등록 주차에 따른 부상, 월요일 강제 2군 이동과 회복·복귀 제한을 추가했습니다. 정규 경기 출전자 표에서 원본 능력치와 이번 경기 피로를 구분하며, AI는 같은 주에 공개된 일정으로 휴식을 계획합니다. DB는 백업 후 버전 7로 확장하고 이미 완료된 경기의 결과·이벤트는 보존합니다. 정책·복원 범위·검증 방법은 [11차 피로·부상 문서](docs/11차_피로_부상.md)를 확인하세요. 게임 날짜는 기존 28주 체계를 유지합니다.

프로필 상세, 계약·연봉·트레이드, FA 계약 협상, 성장·노화·시즌 정산·시상식, 포스트시즌·정규 동률 결정전, AI 기획사의 월요일 전체 로스터 최적화, 다중 세이브 슬롯은 구현하지 않았습니다.

표 전체의 크기를 조절하거나 별도 창으로 분리하려면 [표 패널 도킹·크기 조절 사용법](docs/표_패널_도킹_사용법.md)을 확인하세요. 패널 제목줄과 보라색 경계선을 드래그하고, 상단 **패널 배치 ▾**에서 닫은 표를 다시 열거나 기본 배치를 복원할 수 있습니다.
