# 초기 선수단 편성과 날짜 진행 교착 상태 복구

## 원인

`CalendarService.advance_day()`가 드래프트·최초 선수단·리더의 준비 여부를 검사하지 않아 초기 월요일을 넘길 수 있었습니다. 최초 편성과 리더 지정은 기존 월요일 규칙을 따르므로 수요일에 도달한 미편성 세이브는 진행과 편성이 서로 막혔습니다. 앞선 날짜 표시·안내 수정만으로는 이 교착을 해결하지 못했습니다.

이번 변경은 **날짜 진행 선행 조건과 승인형 초기 날짜 복구**에 한정합니다. 24주 정규 시즌·4주 비시즌, 경기 엔진, 드래프트, AI 정책, 능력치 생성, 일반 월요일 교체 규칙은 유지합니다. 스키마 버전도 6을 유지합니다.

## 날짜 진행 차단

UI와 `CalendarService.advance_day()`가 같은 `initial_setup_reason()`을 사용합니다. 서비스는 SQLite `BEGIN IMMEDIATE` 안에서 현재 날짜를 확인한 뒤 다음 항목을 검사합니다.

1. 최초 드래프트 완료 및 기획사별 16명, 총 160명 지명
2. 플레이어 기획사 선택
3. 플레이어 최초 선수단 편성 완료
4. AI를 포함한 10개 기획사 편성 완료, 편성 대기 선수 없음
5. 플레이어 1군·2군 리더가 해당 선수단에 유효하게 지정됨

미완료면 이유를 반환하고 날짜·일정에 쓰지 않습니다. 하루 진행 버튼은 이유를 확인할 수 있도록 활성 상태를 유지하며, 클릭하면 구체적인 안내를 표시합니다. 버튼을 거치지 않은 API 호출도 동일하게 차단합니다. 이후 기존 미처리 정규 경기·특별전 차단 검사를 그대로 수행합니다.

## 기존 수요일 세이브에서 사용하는 방법

1. 기존 `실행하기.bat`로 실행합니다. 실제 세이브를 자동 복구하지 않습니다.
2. 복구 가능한 경우 상단 날짜 옆에 **초기 날짜 복구** 버튼이 표시됩니다.
3. 버튼을 누르면 다음 확인창이 나옵니다.

   > 초기 선수단 편성을 완료하지 않은 상태로 날짜가 진행되었습니다. 기존 데이터를 백업한 뒤 시즌 1 정규 1주차 월요일로 복구하시겠습니까?

4. 기본 선택은 **아니요**입니다. 취소하면 백업도 만들지 않고 DB를 수정하지 않습니다.
5. **예**를 명시적으로 선택하면 `data/backups/*_before_initial_date_recovery_*.sqlite3`에 SQLite 전체 백업을 생성·무결성 검사한 뒤 날짜만 복구합니다.
6. `game_clock.absolute_day=0`, 날짜 수정 버전 `revision=기존값+1`만 저장합니다. 완료 창에 백업 위치를 안내합니다.
7. **선수단 관리 → 정확히 5명 선택 → 최초 편성 확정 → 1군·2군 리더 각각 저장 → 하루 진행** 순서로 진행합니다. 최초 편성 확정 시 2군 11명과 AI 9개 기획사 편성·리더 지정은 기존 로직이 처리합니다.

드래프트 160지명, 선수 상태와 이름, 능력치·잠재력, 사진 경로, 기획사 자금, 585경기의 대진·콘텐츠·당일 확정 인원, 특별전 6회는 복구 과정에서 변경하지 않습니다. 수요일에 이미 추첨된 필요 출전 인원도 보존하므로 해당 날짜에 다시 도달해도 재추첨하지 않습니다.

## 안전 검사와 저장

`InitialDateRecovery.status()`는 읽기 전용 검사만 합니다. 첫 시즌의 초기 월요일 이후이며 다음 조건을 모두 확인할 수 있을 때 복구를 제공합니다.

- 드래프트 160명 완료 및 플레이어 기획사 존재
- 어떤 기획사도 최초 편성을 시작하지 않았고 리더 기록 없음
- 지명된 160명의 소속이 드래프트와 일치하며 전원 `pro_pending`
- 나머지 선수에게 FA·은퇴·훈련생 등 별도 선수 상태 진행이 없음
- `match_runs` 및 모든 경기 결과·개인 기록 테이블이 비어 있음
- 모든 정규 경기·특별전 상태가 `scheduled`
- 10개 기획사 자금이 각각 초기 10억 원
- 시즌 1의 585경기와 특별전 6회 일정이 온전하며 추가 시즌 일정 없음
- 외래 키 무결성 정상
- 현 버전의 알려진 27개 테이블 구조와 일치

현 버전에는 재정 정산 기능과 거래 원장이 없습니다. 따라서 초기 자금과 알려진 진행 기록을 검사하며, 추후 정산·자금 원장 등 알 수 없는 테이블이나 다른 스키마가 생기면 안전을 확인할 수 없으므로 자동 복구를 거절합니다. 이미 편성·경기·재정 진행이 있는 저장을 초기 상태로 되돌리는 기능은 아닙니다.

승인된 API 호출도 `approved is True`를 요구합니다. 확인창에 표시했던 날짜·수정 버전·전체 저장 데이터 해시를 트랜잭션 안에서 재검증합니다. 승인 이후 다른 창에서 수정했다면 재승인을 요구합니다. `BEGIN IMMEDIATE` 잠금으로 다른 쓰기를 차단한 상태에서 별도 읽기 연결로 백업하고, 성공한 뒤 날짜를 변경합니다. 날짜 이외의 행이 바뀌지 않았는지도 다시 해시로 검증합니다. 백업 실패·날짜 저장 실패·예상하지 못한 트리거 부작용은 전체 트랜잭션을 취소합니다. 동시 승인 두 건 중 한 건만 날짜를 복구하며 수정 버전도 한 번만 증가합니다.

불가 조건이면 날짜를 변경하지 않고 사유를 표시합니다. 원본을 유지한 채 진행 전 백업을 별도 복사본으로 열어 확인하거나 개별 저장 상태 점검이 필요하다는 안내를 제공합니다. 전체 세이브 재생성·강제 날짜 변경은 하지 않습니다.

## 자동 테스트

```powershell
$env:QT_QPA_PLATFORM = 'windows'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

복구 전용 테스트는 취소와 명시적 승인, 백업 원본 완전 일치, 날짜 이외 전체 행 보존, 경기 기록·자금 변동·정산 테이블·부분 편성 차단, 오래된 승인·동시 승인, 백업·저장 실패의 롤백을 검사합니다. GUI에서는 표에서 5명을 선택하고 편성 버튼을 누른 뒤 콤보 선택과 양군 리더 저장 버튼을 누르고 재실행 상태와 하루 진행까지 확인합니다.

실제 세이브에 대한 복구는 테스트용 복사본에서만 실행합니다. 실제 원본의 날짜·선수단·리더·자금·경기 결과를 변경하지 않습니다. 증거 파일은 `.test-artifacts/initial_recovery_before.json`, `initial_recovery_tests.log`, `initial_recovery_full_tests.log`, `initial_recovery_copy_completed.png`, `initial_recovery_verification.json`입니다.

## 최종 결과

Windows 10 / Python 3.13.3 / PySide6 6.12.0, Qt `windows` 플랫폼에서 **전체 162개 테스트 통과(66.810초)**. 복구 전용 16개 테스트를 포함합니다. 실제 수요일 세이브의 복사본에서 GUI로 취소·승인·최초 5명 확정·AI 9곳 편성·양군 리더 저장을 검증했습니다. 재실행 후 날짜·선수단·리더 보존과 화요일 일반 변경 차단도 통과했습니다.

원본 DB의 27개 테이블 전체 행 데이터 해시와 원본 이미지·로고 320개의 파일명·내용 해시는 작업 전과 일치했습니다. 원본은 DB 버전 6, `absolute_day=2`, 날짜 수정 버전 3, 편성·리더 0건, 드래프트 160명, 일정 585경기·특별전 6회, 경기 준비·결과 0건 그대로입니다. 실제 원본에 복구를 실행하거나 복구용 백업을 생성하지 않았습니다. 사용자가 앱에서 **초기 날짜 복구**를 눌러 명시적으로 승인하면 그때 실제 백업과 날짜 복구가 실행됩니다.
