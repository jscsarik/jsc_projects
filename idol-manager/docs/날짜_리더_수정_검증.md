# 날짜 표시와 리더 지정 집중 수정

후속으로 최초 편성 전 날짜 진행과 수요일 교착 상태를 수정했습니다. 최신 복구 기능과 사용법은 [초기 편성 교착 복구](초기_편성_교착_복구.md)를 확인하세요. 아래 내용은 앞선 날짜 표시·안내 수정 당시의 조사 기록입니다.

## 실제 세이브 읽기 전용 조사

조사 대상은 `data/idol_manager.sqlite3`입니다. 먼저 읽기 전용 SQLite 연결로 아래 상태와 전체 27개 테이블의 행 데이터 해시를 기록했습니다. 실제 세이브를 재생성하거나 날짜·선수단·리더를 변경하지 않았습니다.

| 항목 | 조사 결과 |
| --- | --- |
| DB 버전 | 6 |
| `absolute_day` / 날짜 수정 버전 | 2 / 3 |
| 계산된 날짜 | 시즌 1 · 정규 1주차 · 수요일 |
| 요일 인덱스 / `is_monday` | 2 / False |
| 플레이어 기획사 | `jyp` (JYP entertainment) |
| 최초 드래프트 | `completed`, 160명 지명 |
| JYP 최초 선수단 편성 기록 | 없음 |
| JYP 프로 편성 대기 | 16명 |
| JYP 1군 / 2군 | 0명 / 0명 |
| JYP 1군 / 2군 리더 ID | 없음 / 없음 |
| 리더 UI 조건 | 드래프트·플레이어 준비 True, 최초 편성 False, 월요일 False, 작업 중 False → 비활성 |

현재 DB의 날짜와 수정 전 메인·선수단 화면이 읽는 날짜는 모두 수요일로 일치했습니다. `absolute_day=0`을 월요일로 인식하지 못하는 오류는 재현되지 않았습니다. 0일차는 정확히 시즌 1 정규 1주차 월요일입니다.

## 실제 원인과 수정

**날짜 표시:** `MainWindow.__init__()`에서 날짜를 200px 사이드바의 좁은 영역에 넣어 줄이 나뉘었고, 모든 관리 화면 위에 공통으로 보이는 상단 표시는 없었습니다. `show_roster()`, `show_draft()`, `show_squads()`, `show_schedule()`도 전역 날짜를 다시 읽지 않아 다른 창에서 날짜가 바뀌면 기존 값이 남을 수 있었습니다.

날짜와 하루 진행 버튼을 페이지 스택 밖의 공통 상단으로 이동했습니다. 모든 기존 메뉴·기획사 명단·1군/2군 필터에서 상단 날짜가 유지됩니다. 메뉴 진입 시 `CalendarService.state()`에서 다시 읽고, 날짜 진행 성공 및 충돌 안내 후 선수단·일정의 날짜도 갱신합니다. 실제 컴퓨터 날짜를 사용하지 않습니다.

**리더 지정:** 실제 저장 상태는 ‘수요일이며 최초 편성 미완료’이므로 `SquadPage._controls()`의 비활성화 판정 자체는 정상입니다. 그런데 `SquadPage.reload()`의 미편성 안내가 먼저 선택되어 월요일 제한이 가려졌고, 리더 버튼에도 구체적인 비활성화 사유가 없었습니다. 사용자에게는 리더 기능이 아무 반응 없이 막힌 것으로 보였습니다. `SquadService._monday()`와 실제 DB의 리더 저장 트리거는 이미 게임 전용 일수를 사용하고 있었습니다.

현재는 리더 영역에 ‘1군 최초 편성이 완료되지 않았습니다’와 ‘월요일에만 리더를 변경할 수 있습니다’를 동시에 표시합니다. 플레이어 미선택·저장 중·날짜 없음·드래프트 미완료도 각각 안내합니다. `SquadPage._leader()`는 콤보의 내부 선수 ID·플레이어 기획사 ID·선수단 수정 버전을 전달하고, 서비스가 실제 소속·1군/2군·요일을 다시 검사합니다. 잘못된 선수단 ID는 해당 1군/2군 이름을 포함한 오류로 안내합니다.

`game_clock.is_monday(GameDate | None)`를 UI와 서비스가 함께 사용합니다. 최초 편성 유무는 계속 `squad_formations` 기록으로 판단하며 리더가 없어도 편성 완료 상태는 유지합니다. 저장 후 즉시 재조회하고 기존 리더 ID로 콤보 선택과 요약을 복원합니다.

런타임 서비스에는 구형 실제 날짜 SQL 조회가 남아 있지 않습니다. 검색된 `date.fromisoformat(...).weekday()`와 구형 `strftime` 정의는 과거 버전 마이그레이션용이며 유지했습니다. `SquadSnapshot.management_date`라는 호환 필드명은 `GameDate | None` 타입이며 구형 DB 날짜가 아닙니다. 실제 버전 6 DB의 두 리더 트리거도 `absolute_day%7`을 검사합니다.

**실제 세이브의 수요일·미편성 상태는 그대로 유지했습니다.** 월요일 제한을 풀거나, 날짜를 되돌리거나, 최초 편성을 자동 확정하지 않았습니다. 현재 세이브에서는 안내된 조건 때문에 리더 버튼이 계속 비활성인 것이 정상입니다. 저장 상태를 보정하려면 별도의 사용자 승인이 필요하며 이번 수정은 보정을 수행하지 않습니다.

## Windows GUI 검증 방법

```powershell
$env:QT_QPA_PLATFORM = 'windows'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

자동 테스트는 임시 생성 DB와 실제 세이브의 복사본에서만 편성·리더·날짜를 변경합니다. 실제 세이브 복사본의 월요일 시험에서는 표에서 5명을 선택하고 편성 확정 버튼을 누른 뒤, 1군·2군 리더 선택과 저장 버튼 클릭, DB 확인, 창을 닫고 다시 열어 같은 리더가 선택되는 것까지 검증합니다. 화요일 차단·다음 월요일 허용·두 선수 맞교환 후 리더 자동 해제·잘못된 소속 ID 오류도 확인합니다.

증거 파일:

- `.test-artifacts/date_leader_before.json`: 수정 전 실제 상태 및 27개 테이블 해시
- `.test-artifacts/date_leader_before.png`: 수정 전 실제 세이브 복사본 화면
- `.test-artifacts/date_leader_current_fixed.png`: 실제 날짜를 유지한 복사본의 상단 날짜와 비활성 이유
- `.test-artifacts/date_leader_monday_fixed.png`: 복사본에서 월요일 편성·리더 GUI 저장 완료
- `.test-artifacts/date_leader_full_tests.log`: 전체 회귀 테스트 결과
- `.test-artifacts/date_leader_verification.json`: 실제 데이터 보존 최종 대조

최종 검증: **Windows 10 / Python 3.13.3 / PySide6 6.12.0, Qt `windows` 플랫폼에서 전체 146개 테스트 통과(42.067초)**. 실제 DB의 기존 27개 테이블 전체 행 해시는 조사 전과 일치하며 DB 버전은 6으로 유지했습니다. 원본 이미지·로고 320개의 파일명과 내용도 기존 해시와 일치했습니다. SQLite 무결성과 외래 키 검사도 통과했습니다. 실제 세이브에는 수정이나 마이그레이션을 수행하지 않았으므로 이번 작업을 위한 DB 변경·초기화·날짜 보정은 없습니다.
