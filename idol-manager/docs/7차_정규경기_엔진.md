# 7차 개발: 정규 경기 판정과 저장

기획서 7장·15장의 정규 경기 판정을 구현했습니다. PySide6에 의존하지 않으며 실제 세이브의 경기는 자동으로 진행하지 않습니다. 이번 버전에는 경기 실행 버튼·결과 화면·애니메이션을 추가하지 않습니다.

## API

`GameService.matches` 또는 `MatchService(database)`를 사용합니다. **아래 `play` 호출은 지정한 저장 파일에 실제 경기 결과를 저장합니다. 개발 검증은 반드시 임시 DB 복사본에서 실행하세요.**

```python
from idol_manager.match_service import MatchService

matches = MatchService(database)
# 현재 날짜이고 당일 필요 인원이 확정된 정규 경기 ID만 가능.
# 양측 출전자 생략 시 공개된 현재 능력치를 사용하는 AI가 선택.
result = matches.play(match_id)

# 미래 플레이어 선택 화면용 인터페이스: 한쪽만 지정하면 상대는 AI.
# 실제로 실행할 때에는 첫 play 대신 아래 형태를 사용.
# result = matches.play(
#     match_id,
#     lineups={agency_id: [first_team_id_1, first_team_id_2]},
#     representatives={agency_id: first_team_id_1},
# )

saved = matches.result(match_id)   # 결과 없으면 None, 판정을 새로 하지 않음
standings = matches.standings(1)   # 저장된 실제 결과에서만 계산, 미참가도 0점
history = matches.player_records(person_id, season=1, content_id=None)
# result.events: sequence 순으로 보존된 모든 판정.
# 기본 판정 tick 1..60, 리더 phase='leader'/tick=60,
# 데스매치 phase='deathmatch'/round_number=1..N/tick=1..10.
```

수동 선택은 `min(당일 필요 인원, 출전 가능한 소속 1군 인원)`명을 중복 없이 받아 검증합니다. 2군·연습생·타 팀 선수를 지정할 수 없습니다. 대표는 실제 선택된 출전자여야 합니다. 준비가 저장된 뒤 출전자·대표를 변경할 수 없습니다. 완료 경기의 `play()`는 날짜가 지나도 저장된 결과만 반환합니다.

## 판정과 교체 가능한 정책

- 기본 판정은 출전자당 주요 30회·보조 30회입니다. 주요 2종은 각 15회, 3종은 각 10회이고 보조는 주요 이외 능력치에서 매회 독립 추첨합니다. 능력치/100이 성공 확률이며 건강을 더하지 않습니다.
- 실제 출전 1군 리더만 리더십 2회가 별도로 추가됩니다. 팀 점수에는 포함하고 개인 기본 60회와 성장·일반 능력치 기록에는 섞지 않습니다.
- 동점이면 대표별 주요 능력치 10회씩 반복합니다. 5명 콘텐츠는 출전 리더를 대표로 우선합니다. 데스매치는 일반 판정·리더 기록과 분리합니다.
- AI는 주요 30회와 보조 30회의 기대 성공 합계, 출전 리더 보너스를 합산해 경쟁력 있는 인원을 고릅니다. 건강은 동점 우선순위에만 사용합니다. 주요 능력치 합계·건강·ID로 대표를 정하며 잠재력·성장 유형·특별 유망주 정보는 조회하거나 전달하지 않습니다.
- `NoInjuryAvailability.available(player)`를 미래 부상 판정에 연결할 수 있습니다. 아직 부상 정보가 없으므로 현재는 모든 소속 1군이 출전 가능합니다. 건강 0 같은 별도 출전 금지 임계값은 임의로 도입하지 않았습니다.
- `NoMatchEffects.probability(player, skill)`가 기본 확률을 제공합니다. 미래 피로·부상 효과를 이 인터페이스에 주입할 수 있으며 현재는 어떤 페널티도 적용하지 않습니다.
- `ExpectedSuccessLineup`, `choose_representative`, `choose_award`는 각각 별도 정책입니다.

기획서에 없는 세부 정책은 다음과 같이 분리했습니다. 승리·패배 아이돌 동률은 정렬된 후보 중 경기 시드를 사용하는 균등 추첨입니다. 데스매치 10회는 매회 주요 능력치를 독립 균등 추첨합니다(주요 3종에도 적용). 몰수 경기는 실제 대결을 하지 않은 것으로 보아 개인 출전·판정·수상 기록을 만들지 않고 팀 승패·승점만 저장합니다. 양측 몰수패는 두 팀 패배·0점·승자 없음으로 저장합니다.

항상 동점인 대표(양측 모두 성공 확률이 항상 0 또는 항상 1)나 대표 누락은 결과를 확정하지 않습니다. 확률적으로 반복되는 데스매치도 안전 한도 1,000묶음에서 `UnresolvedMatch`로 중단합니다. `match_runs.status='blocked'`와 사유를 저장하며, 승자를 만들거나 재시도에 새 시드를 배정하지 않습니다. 이 경우 날짜 진행은 계속 차단됩니다. 별도 해결 규칙은 이번 단계에 추가하지 않았습니다.

## SQLite 버전 6

버전 5 저장 파일은 먼저 SQLite backup API로 `data/backups/`에 백업한 뒤 단일 마이그레이션 트랜잭션으로 아래 테이블·뷰만 추가합니다. 기존 585경기 대진·확정 인원·드래프트·선수단·리더·자금·능력치·이미지 경로는 변경하지 않습니다.

| 신규 테이블 | 저장 내용 |
| --- | --- |
| `match_runs` | 공개 입력 스냅샷, 난수 시드, 엔진 버전, 준비/차단/완료 상태 |
| `match_results` | 경기별 승자·패자·판정 유형·결과 요약 |
| `match_team_stats` | 리더 보너스 포함 정규 점수(`base_score`)·데스매치·합계 점수, 팀 승패·승점·몰수 여부 |
| `match_player_stats` | 실제 출전, 소속 팀 승패, 일반·리더·데스매치 기록, 성공률, 승리/패배 아이돌 |
| `match_ability_stats` | 선수별·능력치별 주요/보조 시도·성공·실패 |
| `match_events` | 순서·틱·데스매치 묶음·능력치·성공 확률·난수·성공 결과 |

`regular_standings`, `idol_regular_career_stats`, `idol_content_stats`, `idol_ability_stats` 뷰는 실제 경기 행에서 집계합니다. 승점·통산 수치를 별도로 더하지 않으므로 중복 호출로 누적되지 않습니다. 기본 성공률과 리더 포함 전체 성공률을 구분하고 데스매치는 두 성공률에서 제외합니다. 이벤트의 데스매치 단계에는 능력치별 시도와 성공도 남습니다. 경기의 시즌·콘텐츠·날짜·실제 출전 팀을 함께 조회할 수 있어 이후 시즌별 기록·성장·시상식 계산이 가능합니다. 개인 기록은 카탈로그 ID를 참조하므로 향후 소속 이동이나 은퇴로 지워지지 않습니다.

첫 트랜잭션에서 입력·시드를 동결하고 경기 상태를 `in_progress`로 저장합니다. 다음 `BEGIN IMMEDIATE`에서 결과 유무를 재확인한 뒤 판정 계산과 최종 기록 전체·완료 상태를 원자적으로 저장합니다. SQLite 쓰기 잠금은 다른 스레드·프로세스의 중복 계산도 차단합니다. 잠금 대기 한도는 기존 연결의 15초이며 초과 시 재시도 안내 오류를 반환합니다. 준비 후 또는 판정 중 종료되면 결과는 일부도 반영되지 않으며 재실행 시 같은 입력·시드를 사용합니다. 완료 경기 재생·스킵은 저장된 이벤트를 사용합니다. 향후 판정 알고리즘 변경 시 엔진 버전과 이전 준비 데이터의 호환 처리가 필요합니다.

더블헤더 2차는 당일 1차 5경기가 모두 완료되어야 시작합니다. `CalendarService.advance_day()`의 미처리 경기 차단은 유지합니다. 특별전은 자동 완료하지 않으며, 종류도 해당 주 월요일부터만 공개합니다. 지난 주 특별전 종류는 계속 조회할 수 있습니다.

## 검증

```powershell
$env:QT_QPA_PLATFORM = 'windows'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

신규 검증은 기본 판정 횟수·확률 0/100·리더·반복 데스매치·인원 부족·몰수·수동/AI 출전·SQL 비공개 열 조회 차단·개인 기록·동시 스레드/프로세스·준비 후 프로세스 강제 종료·저장 도중/최종 상태 저장 실패의 전체 롤백·재실행·날짜 안전장치·버전 5 마이그레이션·기존 데이터 보존을 검사합니다. Windows Qt 화면에서도 특별전 종류 공개 시점을 검증합니다.

특별전 판정, 실시간 경기 화면, 피로·부상, 성장·노화, 재정 정산, 계약, FA·트레이드 및 시상식 선정은 구현하지 않았습니다.

## 실제 검증 결과

Windows 10 / Python 3.13.3 / PySide6 6.12.0에서 Windows Qt 플랫폼으로 **전체 136개 테스트가 41.378초에 통과**했습니다. PowerShell 실행기의 `-CheckOnly` 환경 검사도 통과했습니다. 상세 로그는 `.test-artifacts/match_full_tests.log`, 실제 데이터 보존 대조 결과는 `.test-artifacts/match_verification.json`에 저장했습니다.

실제 DB는 작업 전 `data/backups/idol_manager_before_match_engine_20261027_033927_250972_KST.sqlite3`에 백업했고, 마이그레이션도 별도로 `data/backups/idol_manager_before_v6_20261027_035501_974817_KST.sqlite3` 백업을 생성했습니다. 기존 21개 테이블의 전체 행 데이터 해시와 원본 이미지 320개(아이돌 310장·로고 10장)의 파일명·내용 해시가 모두 일치했습니다. 585경기 일정, 드래프트 160지명, 310명 소속 상태, 월요일 게임 날짜와 자금·능력치·잠재력·리더 지정을 보존했습니다. 신규 경기 테이블은 모두 0행이며 **실제 세이브의 경기를 실행하지 않았습니다.** 무결성 검사와 외래 키 검사도 통과했습니다.

다른 Windows PC, Python 3.12, 전원 차단에 따른 실제 디스크 고장은 검증하지 않았습니다. 프로세스 강제 종료와 저장 오류는 임시 DB에서 검증했고, 경기 화면과 특별전 판정 등 이번 범위 밖 기능은 구현하지 않았습니다.
